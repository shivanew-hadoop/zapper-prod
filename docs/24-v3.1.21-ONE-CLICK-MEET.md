# v3.1.21 — Host Create Session: first-time Google connection, then one click

## Host behavior

1. Sign in to Zapper (the normal 24-hour trial/subscription checks still apply).
2. Click **Dashboard → Create Session**. The first time, Google prompts you to select an account and grant permission to create Meet rooms. The Google account password and MFA stay on Google's own pages.
3. The backend requests an **OPEN** Meet room, receives its URL, creates the existing six-digit PIN, and shows the URL in a **read-only** field and the PIN below. The host can choose **Open Meet**; Zapper does not automatically join or enable their camera/microphone.
4. Click Create Session again: Zapper uses the securely saved Google connection to create the next room without prompting for sign-in. This works from a browser on desktop or mobile, subject to Google pop-up and account policies.
5. The manually entered Meet-link option remains unchanged under **Use an existing Google Meet link (manual fallback)**. Registration, one-time 24-hour trial, subscriptions, desktop voice-to-text, transcripts, admin tools and PDFs are unchanged.

## One-time administrator setup — required; cannot be skipped by browser automation

Google will **not** let an arbitrary website programmatically create Meet rooms just because its user is logged in to Gmail. The Meet API requires a Google OAuth client belonging to your app, plus user permission. This is not a Zapper-specific limitation.

- In [Google Cloud Console](https://console.cloud.google.com/), select/create a project and **enable Google Meet REST API**.
- In Google Auth Platform, configure the OAuth consent screen. Include the correct audience and authorized test users while the app is in Testing. The Meet `meetings.space.created` permission is sensitive and may require Google verification for public usage.
- Under OAuth Clients, create a **Web application** and add the authorized redirect URI exactly:
  `https://api.zapperapp.in/api/google/meet/callback`
- On **Railway → zapper-prod → Variables** (backend only), set:
  `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URI`.
  The redirect URI must be exactly the one registered in Google. Do not put credentials in GitHub, Vercel or the web source.
- Keep the existing `JWT_SECRET` stable because it protects Zapper tokens and is used to derive the encryption key for Google refresh tokens. Keep the persistent Railway SQLite volume mounted. **Do not reset it.**
- Keep `WEB_ORIGINS` covering the actual web domain, for example `https://zapperapp.in,https://www.zapperapp.in`.
- Push updated code to your GitHub `main` branch; deploy the backend **and** web. Wait for Railway `/health` to report `3.1.21` and for Vercel to deploy the matching frontend.

Only after these values are in place does the Create Session button become enabled. Without them, the manual Meet-link workflow continues to work. Neither ChatGPT nor a ZIP can supply your app-specific Google OAuth credentials.

## Google connection reuse and security

- Zapper requests Google's `meetings.space.created` scope with offline access and PKCE. Google can still require its own login, MFA and consent. A Google refresh token is saved **encrypted at rest** in the existing SQLite database with AES-256-GCM; access tokens are never saved or sent to the frontend.
- Subsequent Create Session clicks use that refresh token on the backend. Only the resulting room URL and six-digit PIN are returned. Tokens are tied to the signed-in Zapper user and current Google OAuth client ID.
- If permission is revoked, expired, or Google's policies require reauthorization, Zapper asks the host to reconnect. A Google OAuth consent screen in **Testing** can issue refresh tokens that expire in seven days, so a stable permanent connection requires the appropriate Google Cloud publishing/verification configuration.
- A popup opened without a usable opener (for example, some mobile browsers) displays the PIN and Meet link itself; return to the original Zapper tab and refresh Recent Sessions to see the created room.
- The four-seat limit restricts **Zapper desktop PIN participants only**. Google Meet itself has no enforced four-attendee cap from this API; anyone with the direct Meet link may join. OPEN access can be restricted by Google account / organization policies, so test with an external Google account.
- The Google Meet REST API does not control an attendee's camera/microphone state, nor does it transmit their speech. Those continue to depend on Google Meet settings and the existing Zapper desktop audio/transcription workflow. No mobile-native voice capture implementation was added.

## Local tests

`cd apps/api && npm run check && npm run smoke`

Tests cover encrypted refresh-token persistence, one-click repeat creation, revoked-token fallback to Google consent, OPEN Meet configuration, one-time OAuth state and PKCE, four Zapper seats, manual creation, registration/trial/expiry, transcripts/PDFs and database migration. Google calls are mocked; **real OAuth and Google Meet join behavior must be tested after production credentials are configured**.
