# Zapper v4.1.1 — Capture host microphone after Google Meet session creation

## Scope

This is an incremental update on **v4.1.0**. It does not change Google OAuth,
meeting creation, PIN issuance, registration, subscriptions, admin controls,
participant seat limits, desktop audio capture, or PDF creation.

After a host creates an **automatic Google Meet** session in the website, Zapper
asks for browser **microphone** permission and streams that host's own voice to
the existing `/stt` -> Deepgram -> live transcript/PDF pipeline.

**No Google Meet tab has to be open to capture the host's local microphone.**
This is a direct local microphone connection, not Google Meet audio access.
It does **not** capture audio spoken by remote Google Meet participants without
someone actually joining Meet and supplying meeting audio through the existing
Zapper desktop application.

## Normal flow

1. Sign in to Zapper as an eligible host.
2. Click Dashboard -> Create Session. Google signs in if needed.
3. Zapper generates the existing Google Meet URL and six-digit PIN.
4. The browser requests microphone permission, **never camera permission**.
5. Allow microphone access. The visible panel reports "Listening" and shows
   recent voice captions. Captions are saved in the *existing* session transcript.
6. Keep the Zapper tab open while recording. Switching to other windows/tabs on
   a supported desktop browser generally preserves the microphone stream.
7. Click **Stop microphone** to stop only host audio capture. The PIN/session
   remains active. Click **Start microphone** to resume.
8. Click **End Session** to stop audio capture, invalidate the PIN and finalize
   the same PDF report as before.

A refresh, tab/browser close, lost microphone permission, system sleep, or
mobile browser suspension can stop microphone capture. After a refresh click
**Start microphone** to resume. No promise is made that a closed or suspended
browser will keep recording in the background.

## Operational requirements

- The API must be deployed alongside the web page; the new UI needs
  `POST /api/sessions/:id/host-audio-token` and the updated `/stt` token check.
- The **existing** `DEEPGRAM_API_KEY`, `JWT_SECRET`, and `WEB_ORIGINS` values on
  Railway stay unchanged. `WEB_ORIGINS` must contain the actual host site, e.g.
  `https://www.zapperapp.in`.
- The website must run over HTTPS to request microphone access (or localhost
  for development). Modern desktop Chrome/Edge is recommended.
- The microphone is used only with browser permission and displays status and
  Stop control. A new session is not silently recorded after the browser closes.
- No additional Railway or Google credential is needed for *local microphone*
  capture beyond the credentials already required by v4.1.0.

## Regression checks

From `apps/api`: `npm run smoke` includes the host-microphone permission tests.
The included browser UI and PCM tests were run locally with mocked mic/API data.
A real microphone, a real Google OAuth flow, and a live Deepgram STT stream still
require production acceptance testing. Do not claim live audio verification
from mocked/local tests alone.

## Privacy note

Users should capture or transcribe audio only with appropriate notice and
consent. Creating a Meet room through Google's REST API does not join that room
or give Zapper access to remote participants' audio.
