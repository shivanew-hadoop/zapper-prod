# Zapper v3.1.20 — Create an OPEN Google Meet from the Host Dashboard

## What changed

- Host Dashboard: **Create Google Meet + PIN** opens Google account selection/authorization. When Google confirms an OPEN Meet, Zapper stores its URL and creates the normal six-digit PIN. The popup then opens the new Meet URL for the host.
- Manual Google Meet link session creation is retained under an expandable fallback. Existing manual sessions, PINs, trial subscriptions, PDFs, desktop capture, admin controls and voice-to-text remain unchanged.
- New Google-generated Zapper sessions can issue **four simultaneously active Zapper desktop PIN tokens**. A new persistent desktop installation ID lets someone re-enter the same PIN without consuming a second seat. The backend detachment endpoint can release a seat, but the current desktop **Leave** button keeps background capture running and therefore does not free a seat. A fifth PIN redemption receives `SESSION_FULL` (409). This limit is **not** applied to old/manual-link sessions.

## Critical limitations

1. Google Meet **does not expose a four-attendee hard cap via this API**. Anyone who gets the direct Meet URL can join the Google meeting, regardless of whether they redeemed a Zapper PIN. This implementation caps only the number of Zapper desktop participants connected through Zapper's PIN system; it does not cap the actual number of Google Meet attendees.
2. The API asks Google for `config.accessType=OPEN` and `entryPointAccess=ALL`; **Google account / Workspace policies determine whether that works**. Zapper refuses to issue a PIN if Google does not confirm OPEN access. This avoids promising admission-free entry for a restricted room.
3. Google OAuth consent **cannot be bypassed**. The host will see Google's account selection and permission screen as required.
4. The integration requires a Google OAuth Web application client and enabled Google Meet REST API. **No Google tokens or Google credentials are included in this ZIP.** Each attempt exchanges a one-time code, uses the access token to create one space and discards the token.
5. The desktop Leave button intentionally retains background capture, so it does **not** release a participant slot. Four distinct desktop installations can redeem the PIN; reconnecting from the same updated installation reuses its seat. Older installed desktop builds do not send the stable device ID and consume a separate slot on each redemption. If all four seats are occupied by disconnected/crashed clients, the host can end the session and create a new one. Other session lifecycle rules are unchanged.

## Google Cloud configuration (required before deploying)

1. Open [Google Cloud Console](https://console.cloud.google.com/), choose a Google Cloud project (or create one), and enable **Google Meet REST API**.
2. Configure Google Auth Platform / OAuth consent screen, including the correct app name, support email and authorized users. The `https://www.googleapis.com/auth/meetings.space.created` scope may require Google's verification before use by arbitrary public users. If the app is in testing mode, add the hosts as test users.
3. Create an **OAuth client ID** with application type **Web application**. Add this exact Authorized redirect URI:
   `https://api.zapperapp.in/api/google/meet/callback`
4. In your **Railway API service**, set the following environment variables:
   - `GOOGLE_OAUTH_CLIENT_ID` — Google OAuth Web client ID
   - `GOOGLE_OAUTH_CLIENT_SECRET` — Google OAuth Web client secret
   - `GOOGLE_OAUTH_REDIRECT_URI` — `https://api.zapperapp.in/api/google/meet/callback`
   - Ensure existing `WEB_ORIGINS` includes the exact frontend origin where hosts use Zapper, such as `https://zapperapp.in` and `https://www.zapperapp.in`. These origins are used to validate the OAuth popup response and must agree with the CORS settings.
5. Set the redirect URI to the public backend domain you actually use if different from the example above. Add it to the Google OAuth client's Authorized redirect URIs too. Use HTTPS for production.
6. Push `apps/api`, `apps/web` and the single related `apps/desktop/main.js` participant identifier change to GitHub `main`; wait for a new Railway API deployment **and** a new Vercel web deployment. Build/publish the updated desktop application to enable stable device-slot reuse; older desktop versions can still redeem the PIN but use a new slot each time. Check `/health` reports API version `3.1.20`.
7. As an active host, open Dashboard -> Create Google Meet + PIN. Choose a Google account and approve the Google permission prompt. Zapper will generate a PIN only if Google returns a link configured for OPEN access. Test a second account joining without host admission, because organization policies may still restrict joining.

If OAuth is not configured, the new button is disabled, and the existing manual link option remains fully available. No schema reset or Railway volume deletion is required.

## Security / testing

- One-time, ten-minute Google OAuth state is stored in the existing SQLite database; PKCE S256 is used. The callback refuses a reused/expired state. OAuth tokens and Google client secrets are never sent to the frontend.
- The backend checks the Zapper host's login, role and valid trial/subscription **before starting OAuth and again before creating the session**.
- API smoke tests (including trial registration, expiry, admin renewal, legacy PINs, transcript/PDF logic) and mocked OAuth tests pass locally. **Live Google sign-in and native Google Meet joining are not verifiable without real Google Cloud credentials and production deployment**.
